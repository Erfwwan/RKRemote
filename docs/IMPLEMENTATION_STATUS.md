# Implementation status

This branch is a development foundation for the next major RKRemote iteration.

## Implemented in this branch

- Versioned JSON message envelope with an allow-list of message types and a 64 KiB limit.
- One-time, five-minute pairing challenge generator with single-attempt verification and PBKDF2-HMAC-SHA256 derivation.
- TLS-only WebSocket transport requiring a caller-supplied SHA-256 certificate pin.
- Central Android runtime-permission and notification-listener checks.
- Visible foreground-session notification with a local stop action.
- Pairing-code UI prototype that explicitly reports that no peer has connected.
- AES-256-GCM payload envelope with random nonces, authenticated associated data, strict size limits, and tamper detection (requires a separately authenticated session key).
- Session command authorization gate requiring an owner-approved active session, exact peer identity, per-capability grants, monotonic sequence numbers, and explicit revocation.
- SAF document repository limited to the tree URI selected by the device owner; bounded file reads and permission-checked deletion. The LAN agent now lists direct-child document IDs, downloads selected direct-child files, and accepts uploads into the selected tree only; transfer limit is 8 MiB per file, names are sanitized, existing files are not overwritten, and the owner-selected SAF grant is the only storage boundary.
- LAN agent/controller on TCP 18765 with temporary bearer token; health check and owner-selected folder metadata listing, plus normalized tap, swipe, and long-press gestures and focused editable-field text insertion when the target owner has manually enabled RKRemote Accessibility. Client handling is bounded (four active workers, sixteen queued clients, header limits and socket timeouts); controller response reads are capped at 16 MiB and IPv4 octets are validated.
- Owner-approved screen capture through Android MediaProjection consent, visible mediaProjection foreground service, in-memory JPEG frame (maximum dimension 1600 px), and authenticated `/screen.jpg` snapshot endpoint;
- Owner-started camera capture through Android CAMERA permission and a dedicated camera foreground service with a persistent stop notification; low-rate JPEG frames (up to 1280×720) are held in memory and read through authenticated `/camera.jpg`. Remote requests cannot start the camera.
- Owner-started microphone capture through RECORD_AUDIO permission and a dedicated microphone foreground service with a persistent stop notification; mono 16 kHz / 16-bit PCM chunks are held briefly in memory and polled through authenticated `/audio/chunk`. Remote requests cannot start the microphone. The controller plays received chunks using AudioTrack.\n- Two-way audio prototype: target owner locally enables PttPlaybackService (mediaPlayback foreground service with persistent stop notification); authenticated POST /audio/ptt accepts only 1–4096-byte PCM chunks while that local service is enabled. The controller captures 16 kHz mono 16-bit PCM only while the PTT surface is held, sends approximately 100 ms chunks, and stops capture on release. Queue is capped at 24 chunks and drops the oldest when full to bound latency. The existing target microphone polling path provides audio in the reverse direction. controller can request one snapshot or poll JPEG snapshots at roughly one per second for a low-rate preview (not continuous video). A separate AccessibilityService requires manual enablement in Android settings and accepts authenticated normalized gestures (tap, swipe, long press) and text insertion into the currently focused editable field. The controller screen image supports direct tap and long press; swipe is currently entered with normalized start/end coordinates. Text insertion uses ACTION_SET_TEXT rather than simulated key events.
- JVM tests for the encryption envelope and command authorization gate.
- Notification history forwarding is implemented as an owner-controlled LAN endpoint: the target must have Android Notification Access enabled and separately enable notification_sharing_enabled locally. /notifications returns at most the latest 100 events from the encrypted local store, with notification text fields capped at 2,000 characters. The controller can request and display the returned history; remote requests cannot enable sharing.
- Existing local setup and encrypted notification store remain in place.

## Not implemented / not production-ready

- Internet relay, cross-network connection, TLS on the LAN socket, or end-to-end authenticated key exchange. The LAN token is a temporary bearer secret sent over the local network; use only on a trusted private Wi-Fi network. The AES-GCM envelope is not yet connected to the LAN transport.
- Durable paired-device identity and key rotation.
- Continuous screen video (the current preview is periodic JPEG polling), keyboard-event emulation and full remote input (gesture and focused-field text insertion are now implemented, but not yet device-validated), continuous camera video, production-grade/low-latency/jitter-buffered voice, synchronized full-duplex VoIP, subfolder navigation and larger/resumable file transfers, contacts/call-log transfer. Notification forwarding is limited to an explicit local opt-in and latest-100 snapshot; incremental sync, remote deletion/acknowledgement, and per-app filters are not implemented. Screen capture is currently a single JPEG snapshot per controller request; it is not a live video stream. File transfer now supports direct-child download and upload in the owner-selected SAF folder with an 8 MiB cap; subfolder navigation, larger/resumable transfers, and camera/microphone and file-transfer physical-device validation remain outstanding.
- Section 7 connection recovery prototype: controller can monitor `/health` and retry idempotent health probes with bounded 1s/2s/4s/8s/15s backoff (5s interval after recovery); the screen-preview loop retries after transient failures instead of stopping immediately. The server now enables address reuse, TCP_NODELAY and keepalive on accepted sockets, reports uptime/active/queued clients in `/health`, surfaces fatal listener errors in the persistent target notification, and closes active sockets/workers on stop. The controller uses TCP_NODELAY/keepalive and endpoint-specific read timeouts. This does not silently restart the target agent after Android kills the process; the owner must start a new visible session. Battery optimization exemptions are not requested.
- The LAN bearer token and snapshots still travel without TLS; worker bounds reduce local resource-exhaustion risk but do not make the protocol safe on untrusted networks.
- Device-farm tests, physical-device and long-duration battery/network tests, release signing, and security review.

The WSS transport, encryption utility, and command gate remain separate foundations. The executable LAN path is a deliberately small TCP protocol with a temporary token; it is not suitable for untrusted networks or internet exposure. Screen snapshots are also sent without TLS and may contain sensitive information visible on the target display. No privileged Android operation is executed from inbound network requests. No privileged operation should be wired to inbound messages until peer authentication, authorization, replay protection, capability consent, and session revocation are integrated and tested.


## Camera and microphone prototype boundary

Camera and microphone capture must be started by the owner from the target phone while the app is visible and after the corresponding Android runtime permission is granted. Each sensor runs in its own foreground service with a persistent notification and a stop action. The LAN endpoints only expose frames or queued audio chunks from a service that is already running; they cannot switch either sensor on. Camera frames and PCM audio chunks are memory-only and are discarded when capture stops. The LAN transport is still plaintext bearer-token HTTP on trusted Wi-Fi only; do not use these media endpoints on public networks or expose port 18765 to the internet. Audio currently uses short polling chunks and is not a jitter-buffered, lossless, low-latency voice transport. Physical-device validation is still required.


## Two-way audio / push-to-talk prototype boundary

The target owner must enable the PTT speaker locally from the app. This starts a mediaPlayback foreground service with a persistent notification and a local stop action. The server rejects incoming PTT chunks unless this service is active; a network request cannot start playback. The controller requires Android RECORD_AUDIO permission and sends 16 kHz mono 16-bit PCM only while the user holds the PTT control. Releasing the control stops capture and cancels transmission. Chunks are bounded to 4096 bytes and queued in memory (maximum 24 chunks; oldest chunks are dropped under pressure). The existing /audio/chunk endpoint carries the target microphone back to the controller, so the prototype supports talk-to-target plus listen-from-target. It is not synchronized full-duplex VoIP, has no jitter buffer or echo cancellation, and should be tested with headphones. All audio still travels over the plaintext LAN bearer-token protocol; trusted private Wi-Fi only. Physical-device tests remain outstanding.


## Notification history forwarding boundary

The notification listener captures posted and removed events only after the device owner manually enables RKRemote in Android Notification Access settings. Events are stored in the existing bounded (500-event) Android Keystore AES-GCM encrypted local store. A second, separate local switch (notification_sharing_enabled) is required before the authenticated LAN /notifications endpoint will return anything. The endpoint also re-checks that Notification Access remains enabled, exports at most the latest 100 events, and caps each exported text field at 2,000 characters. The controller fetches and displays this snapshot on demand; there is no background forwarding or silent remote enablement. Notification payloads still travel over the plaintext LAN bearer-token transport, so use trusted private Wi-Fi only. This does not provide end-to-end encryption. Physical-device validation remains outstanding.


## Section 7 · Connection recovery and diagnostics

The controller's **Auto reconnect** control performs idempotent `/health` probes. After a failed probe it retries with bounded backoff of 1, 2, 4, 8, then 15 seconds; after a successful probe it checks every 5 seconds. The live screen preview also retries after transient network errors and returns to its normal one-second polling interval after recovery. **Check now** performs a single manual health probe. The health response reports agent uptime, active clients and queued clients. The target foreground notification is updated if the LAN listener fails to bind or terminates unexpectedly. Accepted sockets use TCP_NODELAY/keepalive and the client uses separate timeouts for PTT, media, file and normal requests. Retry logic is limited to read-only health checks and screen snapshots; non-idempotent commands and file transfers are never automatically replayed.

The target agent remains START_NOT_STICKY by design: if Android terminates the target process, it does not silently restore remote access or reuse a previous token. The owner must reopen RKRemote, generate a fresh temporary token and start a new visible session. No battery-optimization exemption is requested automatically. OEM power management can still suspend background work; manual battery settings may be needed during long sessions. Physical-device and long-duration tests remain outstanding.


## Section 2 · agreed continuous video specification (not yet implemented)

The user has approved replacing screen JPEG snapshots/polling with a continuous H.264 video stream, encoded/decoded with Android MediaCodec, with the longest image dimension capped at 480 px, a target of at least 5 fps where supported, bounded latest-frame delivery that drops stale frames, and direct touch interaction on the rendered stream. Remote rotation control is not required. The detailed requirements and acceptance criteria are in [docs/SECTION_2_LIVE_VIDEO.md](SECTION_2_LIVE_VIDEO.md). This is currently a specification-only commit: executable code still uses JPEG snapshots up to 1600 px and approximately one-second polling. The current plaintext HTTP LAN transport must be replaced by the authenticated encrypted transport before live screen data is sent over it. Do not claim continuous video is implemented or tested yet.
